# 技术难点分析

更新时间：2026-05-14

## 当前技术路线

项目当前采用“稳定演示优先，真实模型可切换”的路线：

- 前端：React + Tailwind CSS + Vite demo。
- 后端：Vercel Serverless API routes + Node.js。
- 文本理解：智谱 GLM-4.7-flash，使用 OpenAI-compatible API。
- 图像生成：智谱 CogView-3-Flash 云端生图，Stable Diffusion WebUI / PixelRTXL 作为可选本地图生图方案。
- 兜底链路：Mock service，保证无 key、无 GPU、无网络时仍能完整演示。

早期 OpenAI GPT / DALL-E / Express 方案已作为备选和历史探索保留，不再作为当前交付口径。

## 核心技术难点

### 1. 像素风格一致性

**难点**

- 真实生图模型容易生成“像素感贴图”而不是真正统一的像素游戏资产。
- 透明背景、白底、主体居中、比例稳定都需要 prompt 和后处理一起约束。
- 菜品需要和现有美术素材保持温暖手绘像素童话厨房风。

**当前方案**

- 后端 prompt skill 自动注入 `docs/美术风格定义.md`、`docs/美术实现规范.md` 和 `assets/art-library/manifest.json`。
- CogView-3-Flash 负责默认云端生图；如使用本地模式，Stable Diffusion WebUI 可通过 PixelRTXL checkpoint 控制风格。
- Mock 模式使用 CSS/色板生成占位菜品，避免演示中断。

### 2. 生图延迟和演示节奏

**难点**

- txt2img 和 img2img 可能超过 10-30 秒，现场演示不稳定。
- Vercel Serverless 对长任务不友好。

**当前方案**

- Demo 默认 `AI_KITCHEN_USE_MOCK=true`，稳定跑完整流程。
- 真实链路只替换 API 内部实现，前端字段保持一致。
- 若真实生图上线，建议改为任务队列 + 轮询，或将图像服务独立部署。

### 3. 情绪理解与结构化输出

**难点**

- 玩家输入开放，模型需要提取情绪概念、视觉概念、菜名、融合提示。
- 输出不稳定会直接影响前端展示和反馈评分。

**当前方案**

- `api/_lib/prompt-skill.js` 使用结构化 JSON 输出约束。
- `api/_lib/llm-client.js` 提供 JSON 提取容错。
- `api/_lib/ai-pipeline.js` 对模型输出做 normalize，并保留 fallback。

### 4. 客人库扩展

**难点**

- 客人不只是名字，需要有情绪目标、开场白、引导话术、色板、反馈风格和菜名语义。
- 前端和后端各有一份 mock 数据，容易不同步。

**当前方案**

- v1 已扩展到 6 个客人。
- 菜名库已改为按 `guestId` 取值，新增客人不会误用旧角色菜名。
- 测试覆盖客人字段完整性和新增角色菜名选择。

### 5. 部署边界

**难点**

- Vercel 适合前端与轻量 API，不适合长时间 GPU 生图。
- 本地 WebUI 地址不能直接服务线上用户。

**当前方案**

- 比赛展示推荐本地 mock 或本地真实模型联调。
- 线上展示可先用 mock，真实模型作为技术说明。
- 后续如需生产化，应接独立图像服务、对象存储和任务队列。

## 当前优先级

### P0

- 保证 `npm run check`、`npm test`、`npm run build:demo` 通过。
- 保证 mock 模式完整演示。
- 保证文档、代码、展示脚本技术口径一致。

### P1

- 联调智谱 GLM-4.7-flash + CogView-3-Flash。
- 给 6 个客人补齐独立像素头像。
- 优化一局流程里“为什么输入两轮”的引导。

### P2

- 引入缓存或任务队列。
- 支持 3-4 轮深聊模式。
- 增加更多客人、稀有料理和成就反馈。
